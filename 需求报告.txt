二、需求 R-001：角色权限控制                      【状态：已确认，待实现】
================================================================================

--------------------------------------------------------------------------------
2.1 背景
--------------------------------------------------------------------------------

现状：users 表已有 role 列，UserDAO 也把角色读出并放入 User 对象，但没有任何一处
代码使用它。User.getRole() 与 AuthController.getCurrentUser() 均只有定义、没有
调用者。因此 admin 与 agent 登录后功能完全相同——登录只完成了身份认证（你是谁），
未做授权（你能干什么）。该「有字段、无逻辑」的状态属预留未接线。

--------------------------------------------------------------------------------
2.2 权限矩阵
--------------------------------------------------------------------------------

    操作                ADMIN      AGENT
    ----------------------------------------
    查看房屋列表         允许       允许
    添加房屋             允许       允许
    删除房屋             允许       禁止
    查看客户列表         允许       允许
    添加客户             允许       允许
    删除客户             允许       禁止

    即：AGENT 持有 6 项权限中的 4 项，仅两个「删除」权限被收回。

设计原则：写操作放开，删除操作收回。删除是系统中唯一不可逆的操作，收回它即可挡掉
          绝大多数事故；而新增数据是经纪人的本职工作，禁止会导致系统无法正常使用。

补充（阶段二实施时明确）：阶段二新增的「编辑」功能按同一原则处理——它属于写操作，
          因此 ADMIN 与 AGENT 均可使用，未纳入收回范围。若认为改写既有数据同样敏感，
          可将其并入删除权限，收归 ADMIN 独有。

--------------------------------------------------------------------------------
2.3 技术方案
--------------------------------------------------------------------------------

采用「全局会话 + 权限点」方式，校验分两层：

    第一层  View 层        按权限隐藏或置灰按钮        （负责体验）
    第二层  Controller 层  调用前拦截校验              （负责真正的防护）

必须做两层的原因：现有按钮是直接通过 addActionListener 绑定到 Controller 的，
setEnabled(false) 只是不让点，代码层面毫无防护，换任何入口直接调 Controller 均可绕过。

新增两个类（置于 util 包）：

    Permissions   定义 6 个权限点，并维护「角色 → 权限集合」映射表
                  ADMIN 拥有全部 6 项；AGENT 持有 4 项（不含两个删除权限）

    Session       保存当前登录用户，对外提供 Session.can(权限) 判断
                  安全底线：未登录、或角色字符串无法识别时一律返回 false
                  （fail-safe：宁可少给权限，不可错给权限）

--------------------------------------------------------------------------------
2.4 改动清单（2 个新增，6 个修改；Service 与 DAO 保持不变）
--------------------------------------------------------------------------------

    util/Permissions.java               新增   权限常量 + 角色权限映射表
    util/Session.java                   新增   当前用户保存 + can() 判断
    controller/AuthController.java      修改   登录成功写入 Session，退出时清空
    view/MainView.java                  修改   标签页按权限启用；显示当前用户与角色
    view/HouseView.java                 修改   删除按钮按权限置灰并设置悬停提示
    view/CustomerView.java              修改   同上
    controller/HouseController.java     修改   deleteHouse 开头加权限拦截
    controller/CustomerController.java  修改   deleteCustomer 开头加权限拦截

不涉及数据库结构变更，users.role 列已在用。

--------------------------------------------------------------------------------
2.5 边界与注意事项
--------------------------------------------------------------------------------

1. MainView 是复用的同一个实例。它在 RealEstateSystem.main() 中、登录发生之前就
   已构造完成，退出后再次登录仍复用该对象。因此权限应用逻辑必须写成可重复调用的
   方法，showMainView() 与 logout() 中都要调用，否则第二次登录会残留上次的权限状态。

2. 魔法字符串清理。目前 "ADMIN" / "AGENT" 散落在代码各处，拼写错误会静默失效，
   建议一并提取为常量或枚举。

3. 权限不足的兜底提示。Controller 拦截触发时应弹出明确的「权限不足」对话框并
   返回 false，以便万一绕过界面时也能立刻定位原因。

4. 与 BUG-001 的联动。退出登录流程本身存在缺陷（见第六章），本次实现时应一并
   修复，否则权限状态无法正确重置。

3.3 第 1 轮结论：技术底座                        【已确认】
--------------------------------------------------------------------------------

决定：引入 FlatLaf 3.7.2（Apache-2.0）。放弃纯 Swing 手写与 Darklaf 等备选。

选型依据（2026-09-16 核实）：

    方案       最新版本    发布时间      Stars    许可         形态        体积
    ------------------------------------------------------------------------
    FlatLaf    3.7.2      2026-07-09    ~4,215   Apache-2.0   单 jar      992 KB
    Darklaf    3.1.1      2025-09-16    ~473     MIT          多模块      合计更重
    JTattoo    1.6.13     2019          ~300     Apache-2.0   单 jar      ~1.2 MB
    BeautyEye  1.0        2014          ~1,200   GPL v3       单 jar      ~600 KB

三条关键理由：

    1. 单文件依赖。Darklaf 需引入 core 加主题再加若干依赖模块，对课程项目不划算。
    2. 许可风险。BeautyEye 为 GPL v3（传染性许可），项目未来若交付或商用存在
       合规问题；FlatLaf 为 Apache-2.0，可自由使用。
    3. 维护状态。JTattoo 与 BeautyEye 均停滞多年，且视觉风格停留在渐变加光泽的
       年代，与本需求「现代化」的目标相反。

FlatLaf 附加优势：自带 HiDPI 缩放适配；内置浅色 / 深色 / IntelliJ / Darcula 四类主题；
支持 JSON 主题文件与 UIManager.put() 定制；被 Burp Suite、Ghidra、jadx、
Apache NetBeans 等软件实际使用。

落地方式：

    Maven 坐标   com.formdev:flatlaf:3.7.2
    离线方案     下载 flatlaf-3.7.2.jar 放入 com.realestate/lib/
                 （与 mysql 驱动同一目录，一并提交进仓库）
    启用方式     在创建任何 Swing 组件之前调用 FlatLightLaf.setup();
    下载地址     https://repo1.maven.org/maven2/com/formdev/flatlaf/3.7.2/flatlaf-3.7.2.jar

已知代价：仓库体积增加约 1 MB（由 2.4 MB 增至约 3.5 MB）。

3.4 第 2 轮结论：整体视觉风格                      【已确认】
--------------------------------------------------------------------------------

决定：采用「现代清爽」方向。

四个候选方向对照：

    方向        主色        圆角     气质特征              未选原因
    --------------------------------------------------------------------------
    专业稳重    #1F3A5F    4px     政企 / 银行系统感     偏保守，上限只是"看起来正规"
    现代清爽    #2F7BD8    14px    互联网 SaaS 后台感    → 选中
    温暖亲和    #C2703D    16px    面向客户的亲和力      暖色配数据表格易显脏，
                                                           行数一多界面会发灰
    紧凑高效    #3B4A5A    3px     专业工具软件感        与美化目标方向相反

选择「现代清爽」的三条理由：

    1. 表格是本系统的主角。房屋列表 7 列、客户列表 4 列，白底浅灰是数据展示的
       最优解，暖色与深色都会干扰阅读。
    2. 改动量最小。与 FlatLaf 默认外观方向一致，后续定制属锦上添花，无需与
       默认样式对抗。
    3. 展示稳健。干净明亮的界面在任何投影仪与截图场景下都不易出问题。

深色主题：本质属配色决策，并入 3.5 节的第 3 轮一并讨论。

--------------------------------------------------------------------------------
3.5 第 3 轮结论：品牌主色与配色体系                【已确认】
--------------------------------------------------------------------------------

决定一：品牌主色采用「明亮蓝」，色值 #2568BE。

    候选       主色       白字对比度    判断
    -------------------------------------------------------------------------
    明亮蓝     #2F7BD8    4.25:1       略低于 AA；改用深一档 #2568BE 即达标
    青绿       #0E9A8A    3.52:1       不达 AA
    靛紫       #5A5AD6    5.45:1       对比度最佳，但商务系统中略显跳跃
    琥珀橙     #D9812F    2.99:1       明显不足，且橙色普遍代表警告语义

    WCAG AA 对小字号文本的对比度要求为 4.5:1。

    最终取 #2568BE（而非初选的 #2F7BD8），白字对比度由 4.25:1 提升至 5.52:1，
    视觉差异可忽略，属零成本改进。

决定二：仅提供浅色主题。

    调整记录：第 3 轮曾确定「浅色为默认 + 深色可切换」；第 10 轮汇总时用户决定
              取消深色主题，仅保留浅色。本决定为最终版本。

    调整带来的收益：

        1. 无需为每一轮定制的颜色额外提供深色映射，整体工作量减少约一半。
        2. 侧边栏图标（第 8 轮）只需一套，无需考虑深色下的染色处理。
        3. 无需处理「硬编码颜色在深色下暴露」的问题——该项原本是验收清单中
           最易遗漏的一条。

    深色映射色值（原方案，保留备查。若日后需恢复深色主题可直接取用）：

        窗口背景    #2B2D30
        内容背景    #1E1F22
        正文文字    #DFE1E5
        次要文字    #9DA3AC
        边框        #4E5157
        强调色      #4A88D8   （#2568BE 的深色提亮版）

3.6 第 4 轮结论：登录页布局                        【已确认】
--------------------------------------------------------------------------------

决定：采用「左右分栏」布局——左侧品牌区 + 右侧登录表单。

四个候选布局对照：

    布局                 特点                              未选原因
    --------------------------------------------------------------------------
    居中卡片             浅灰底 + 居中白卡                  设计感最弱，与普通模板
                                                            登录页高度雷同
    左右分栏             左侧品牌区 + 右侧表单              → 选中
    全屏主色 + 浮层卡片  主色铺满，中间浮白卡               主色面积过大易腻；深色
                                                            模式下刺眼，映射难调
    顶栏主色 + 表单      顶部一条主色标题栏 + 下方表单      更像工具软件，设计感一般

选择「左右分栏」的三条理由：

    1. 唯一具备品牌区。系统名（9 个字）在居中卡片与全屏方案中只能作为标题挤在

    2. 主色面积适中。比居中卡片存在感强，又不像全屏方案那样铺满。
    3. 深色主题下依然成立。左栏改为深灰底 + 提亮强调色 #4A88D8 即可，结构无需重做。

配套调整清单：

    登录窗口尺寸   600 × 400  →  约 760 × 460（否则右侧表单区过窄）
    左栏内容       系统名 + 三行功能文案
    右栏内容       提示语「欢迎回来」+ 用户名 / 密码输入 + 主色登录按钮

3.7 第 5 轮结论：主窗口布局与导航结构              【已确认】
--------------------------------------------------------------------------------

决定：采用「可折叠侧边栏 + 顶部应用栏 + 底部状态栏」三栏结构。

四个候选结构对照：

    结构                             特点                     未选原因
    ---------------------------------------------------------------------------
    应用栏 + 顶部标签页               不占横向宽度，兼容现有    缺少侧边栏形态，
                                      JTabbedPane               扩展性一般
    侧边栏 + 应用栏                   最"现代后台"，占 96px     只有 2 个模块，
                                                               侧边栏会显得空
    标签页 + 底部状态栏               改动最小                  底部信息存在感弱
    可折叠侧边栏 + 应用栏 + 状态栏     功能最完整                → 选中

最终结构分工：

    顶部应用栏     系统名 / 当前用户与角色 / 主题切换 / 退出登录
    左侧侧边栏     模块导航，展开 96px、收起 38px
    中部内容区     工具栏 + 数据表格
    底部状态栏     记录数 / 当前操作状态

已知代价：侧边栏比纯顶部标签页多占横向宽度，并多出一套展开/收起状态需要维护。
          因此主窗口尺寸需由 900 × 650 调整为约 1100 × 700，否则 7 列的房屋表格
          在侧边栏占位后会过于拥挤。

--------------------------------------------------------------------------------
3.8 第 6 轮结论：数据表格样式                      【已确认】
--------------------------------------------------------------------------------

决定一：表格行采用「悬停 + 选中」两层视觉状态。

    方案                  状态层数   未选原因
    ---------------------------------------------------------------------------
    仅选中高亮            1 层      鼠标滑过无任何反馈，无法判断行是否可交互
    悬停 + 选中           2 层      → 选中
    斑马纹 + 选中         2 层      无悬停反馈，静态感强，像报表
    斑马纹 + 悬停 + 选中  3 层      三种底色叠加，视觉噪音偏大

选择理由：

    1. FlatLaf 原生支持，零额外代码。斑马纹方案需自写单元格渲染器（约 20 行），
       且因项目采用双主题，还需额外维护一套深色斑马纹配色，成本翻倍。
    2. 现有操作流程为「选中行 → 点击删除 → 确认框」，两层反馈已足以建立
       「正在操作哪一行」的认知。
    3. 底色越少，数据阅读越干净。

决定二：表格行高由 30px 调整为 38px。

    候选              说明
    ----------------------------------------------------
    30px（原值）      最紧凑，但中文在 13px 字号下显拥挤
    38px              → 选中。一屏约 13 行，呼吸感合适
    44px              更宽松，一屏仅约 11 行
    自动计算          交由 FlatLaf 按字体推算

--------------------------------------------------------------------------------
3.9 第 7 轮结论：按钮与表单控件                    【已确认】
--------------------------------------------------------------------------------

决定一：按钮采用「实心主色 + 红字红边删除」三层体系。

    角色        样式                            用途
    ------------------------------------------------------------------------
    主按钮      主色 #2568BE 实心 + 白字        添加房屋（页面主要操作）
    危险按钮    红字 #D9534F + 同色描边          删除房屋（不可逆操作）
    次要按钮    灰字 + 灰描边 #C9CDD1            刷新数据
    禁用态      灰底 #F0F1F3 + 灰字 #A8ADB5       无权限时（对应 R-001 权限控制）

四个候选体系对照：

    体系                          未选原因
    ------------------------------------------------------------------------
    实心主色 + 红字红边删除       → 选中
    实心主色 + 实心红色删除       两个实心按钮争抢注意力，次要按钮被压住；
                                  红色实心在工具栏中形似"紧急按钮"
    全描边，靠文字色区分          缺少主操作引导；且禁用态仅边框变浅，
                                  与正常态几乎无法分辨
    实心主色 + 全灰描边           删除属不可逆操作却无任何视觉提示，容易误点

选择理由：

    1. 危险操作需要"可辨识"而非"抢眼"。红字红边足以让用户在点击前意识到这是
       删除操作，而描边的视觉重量低，不会与主操作争夺注意力。
    2. 禁用态对比鲜明。灰底灰字与正常态区分明显，这对 R-001 权限控制至关重要——
       无权限用户应一眼看出"是权限不够"，而非怀疑"按钮坏了"。

决定二：添加对话框采用「分组表单」布局。

    分组划分（与 HouseController.addHouse 的参数结构一一对应）：

        房屋信息    房屋ID / 户型 / 面积 / 地址
        房东信息    房东ID / 房东姓名 / 房东电话

    选择理由：

    1. 字段本身存在天然语义分组，显式分组可降低填错率。
    2. 与现有 addHouse(id, type, area, address, landlordId, landlordName,
       landlordContact) 前 4 + 后 3 的参数结构完全对应。
    3. 加分组标题后对话框高度增加有限，信息层级却明显清晰。

    未选方案：两列表单（最紧凑但无分组）；单列窄表单 + 通栏按钮（属移动端做法，
              桌面软件中不自然，且 7 个字段需排 7 行导致对话框过高）。

3.11 第 9 轮结论：提示与反馈方式                   【已确认】
--------------------------------------------------------------------------------

决定一：采用「轻提示 + 模态确认框」双轨体系。

    反馈类型                形式                              是否打断
    ------------------------------------------------------------------------
    操作成功（添加 / 刷新）  右下角轻提示，约 2 秒后自动消失    不打断
    删除确认                模态确认框（保留）                打断
    错误提示                模态对话框（保留）                打断

核心思路：把反馈分为"必须确认的"与"知道了就行的"两类，只让前者打断操作流。

四个候选体系对照：

    体系                     未选原因
    ------------------------------------------------------------------------
    全部保留弹框             每次操作都需点击「确定」，录入多条数据时干扰明显
    轻提示 + 确认框          → 选中
    底部状态栏提示           状态栏已用于显示当前用户与主题切换，会拥挤；
                             且窗口底部文字容易被忽略
    自绘统一对话框           解决了视觉一致性，但未解决"每次都要点确定"的
                             核心问题

视觉一致性补充：引入 FlatLaf 后，JOptionPane 会自动应用 FlatLaf 的绘制风格，
                因此"弹框与界面风格不统一"的问题已由 FlatLaf 自动解决，
                无需自绘对话框。

实现成本：轻提示为自定义组件（约 50 – 80 行代码）；确认框直接调用 JOptionPane，
          FlatLaf 自带美化，无需自写对话框。

决定二：删除确认框的默认焦点置于「取消」。

理由：删除不可逆。若默认焦点落在「确定」，用户依习惯敲回车即会删除数据；
      默认焦点置于「取消」则必须主动点击「确定」，代价仅为一次点击。

四、需求 R-003：房屋状态（空置 / 已租出）        【状态：已实施 2026-09-17】
================================================================================

4.1 背景与问题

用户发现：把带看记录的结果改为「已成交」后，房屋管理页没有任何变化。

核实后的现状：

    · houses 表结构为 id / type / area / address / landlord_id —— 没有任何状态
      字段。因此「成交」这件事只活在 viewings 表里，房屋那边一无所知。
    · 用户库中房屋 101 已有 1 条「已成交」带看记录，房屋 22 有 1 条「意向中」，
      其余 4 套无带看记录。

4.2 核心决策：状态存在哪里（已确认）

曾考虑「不加字段、状态由带看记录派生」，但被否决，原因是它有两个缺陷：

    ① 带看记录对客户的外键是 ON DELETE CASCADE（G-008 定下的）。删掉一个客户
       会连带删掉他的带看记录，那套已租出的房子就会在界面上静默变回「空置」——
       没有任何提示，且方向危险（把已租出的房子当空置继续推荐）。
       单独删掉那条带看记录，后果相同。
    ② 表达不了带看管不到的两件事：租客退租；以及没走带看流程就直接成交。

因此确定：状态是房屋自己的属性，带看成交只是「触发它改变的一个事件」。

4.3 三项确定的设计

    决定一、状态取值：二值 —— 「空置」/「已租出」，默认「空置」。
           以后若需要增加「已售出」，枚举加一个值即可，不影响已有数据。

    决定二、成交自动置位，但不自动回退。
           带看记录结果变为「已成交」时，自动把该房屋置为「已租出」；
           但把已成交改回其它结果、或删掉该记录时，房屋状态不动，
           仅在界面上提示「该房屋状态仍为已租出，如需调整请到房屋管理页」。

           理由是两种方向的错误代价不对称：
             · 以为是空置、其实已租出 → 重复推荐，对客户失信；
             · 以为是已租出、其实空置 → 只是少推一套，看一眼带看记录即可发现。
           所以自动只往「占用」方向走，往「释放」方向必须人工确认。

    决定三、状态可在房屋编辑对话框里手动修改。
           这是必需的而非补充：退租、以及线下直接成交都不经过带看记录。

4.4 界面改动（已确认）

    ① 房屋列表新增「状态」列，用彩色标签呈现：
           空置   → 灰底灰字
           已租出 → 主色底、白字（沿用 Theme.ACCENT）
       位置放在「地址」之后，而不是排在最末 —— 它与「这是哪套房」一起扫视
       更自然，也不至于被房东电话列挤到看不见。

    ② 房屋列表新增「状态」下拉筛选（全部 / 空置 / 已租出），与搜索框并列。
       复用既有的内存过滤逻辑，因此「导出 CSV」依旧导出当前筛选后的结果。

    ③ 添加 / 编辑对话框在「房屋信息」组末尾新增「状态」行，独占一行。
       原因是它是下拉而不是文本框，挤进两列网格会与其他字段对不齐；
       独占一行的写法与既有的「房东」行一致。

    ④ 概览页把「平均面积」卡换成「空置房源」卡（仍是 5 张）。
       空置房源是这个系统里最接近「库存」的指标，值得有独立卡位；
       平均面积的参考价值相对最低。

4.5 既有数据的初始化（已确认）

    按现有带看记录推导：房屋 101 已有「已成交」记录，迁移时直接标为「已租出」，
    其余 5 套为空置。这样迁移本身就顺带验证了「成交 → 自动置位」这条链路。

    迁移前先整表备份 houses 到 .workbuddy/backup/（已 gitignore，不入库）。

4.6 改动清单（预估）

    数据库      houses 表新增 status 列
                （VARCHAR(10) NOT NULL DEFAULT '空置'）
                DatabaseUtil.initializeDatabase() 的建表语句同步加该列，
                并为已有库补一次可重复执行的 ALTER TABLE

    新增        House 内集中定义状态常量，与 Viewing.RESULT_* 同一写法

    修改        House            增加 status 字段与 getter
                HouseDAO         查询带出 status；新增 updateStatus；
                                 insert / update 写入 status
                HouseService     透出 updateStatus
                HouseController  校验状态取值合法性
                ViewingController 新增 / 编辑带看结果为「已成交」时，
                                 在同一事务内把房屋置为「已租出」
                HouseView        状态列 + 状态筛选 + 对话框状态行 + 状态标签渲染
                StatsDAO         增加空置数统计
                Overview / OverviewView  用「空置房源」替换「平均面积」

    权限        改状态属「写」操作。按 R-001 的「写放开、删收回」原则，
                ADMIN 与 AGENT 均可修改（用户未提出异议）。

4.7 边界与注意事项

    · 「成交自动置位」必须与带看记录的写入在同一事务内完成，否则可能出现
      「带看记录已写成已成交、房屋状态却没改」的不一致。可沿用 G-010 已有的
      事务写法。
    · 状态取值要集中定义，不要在多个文件里散写字符串字面量。
    · 按状态筛选后取行仍须经 convertRowIndexToModel（G-005 已有的坑）。
    · 「不自动回退」这一条必须在界面上给出提示，否则用户会当成 bug 报回来。

    · 与 G-018 的关系：删房屋时会一并清理无引用的房东，状态随房屋一起消失，
      不产生额外影响。

4.8 实施记录（2026-09-17，已完成）

    一、数据层

        · houses 表新增 status 列（VARCHAR(10) NOT NULL DEFAULT '空置'）。
          DatabaseUtil 的建表语句已含该列，并为「改造前建的库」补了一次
          「先查 information_schema 再 ALTER」的结构补充——可重复执行。
          此处刻意没用 ALTER TABLE ... ADD COLUMN IF NOT EXISTS：那是 MariaDB
          的扩展，MySQL 不支持，照抄会得到语法错误。
        · House 增加 status 字段与 getter；状态常量集中在 House 内
          （STATUS_VACANT / STATUS_RENTED / STATUSES），构造时把 null 与空串
          回落到「空置」，因此新增时不选也有合理默认。
        · HouseDAO：查询带出 status；新增 / 编辑随整行一起写；
          新增 markRented(Connection, houseId) 供带看成交在同一事务内调用
          ——它刻意接收连接而不是自己开连接，理由见二。

    二、业务层

        · ViewingDAO 的新增与更新改为事务：结果为「已成交」时，在同一事务里
          把房屋置为「已租出」。放同一事务是必需的——否则会出现
          「带看记录已写成已成交、房屋状态却没改」的不一致。
        · ViewingController 的成功提示会带上「（房屋 X 已置为「已租出」）」，
          免得用户以为系统在背后改数据。
        · HouseController 校验状态取值合法性（下拉选不出非法值，但防绕过界面调用）。
        · 反向刻意不处理：改回其它结果或删掉记录都不动房屋状态。

    三、界面层

        · 房屋列表新增「状态」列，位置在「地址」之后（房东三列相应后移）。
          状态渲染为圆角标签：已租出用主色实底 + 白字，空置用浅灰底 + 次级文字色；
          选中行时不画标签、只用选中前景色，否则标签底色会和选中底色叠在一起看不清。
        · 新增「状态」下拉筛选（全部 / 空置 / 已租出），与关键字搜索框并列、
          叠加生效。状态栏计数与 CSV 导出都已跟着改（导出依旧是「当前筛选后的结果」）。
        · 添加 / 编辑对话框在「房屋信息」组末尾新增「状态」行，独占一行。
        · 概览页以「空置房源」替换「平均面积」；底部状态栏也补上了空置数。
        · 带看记录里把「已成交」改成其它结果时，弹出说明框告知房屋状态不会自动回退，
          并指引到房屋管理页处理——不提示的话用户会当成 bug。

    四、与原方案的差异

        1. 原改动清单写了「HouseDAO 新增 updateStatus」与「HouseService 透出
           updateStatus」，实际未做。手工改状态走的是编辑对话框，保存时整行
           一起写（状态是其中一列），单独的更新入口没有调用方，
           为避免留下死代码而删掉。
        2. 连带影响：Formats.average() 原先只服务概览页那张「平均面积」卡，
           现在已无生产代码调用。方法与其测试都保留着——要用回平均面积时直接就有。
           此处如实登记，供日后清理时判断。
        3. 权限按既有约定（写放开、删收回）：ADMIN 与 AGENT 都能改状态。

    五、验证

        · javac 编译 46 个源文件 + 9 个测试文件零报错（79 个 class）。
        · 单元测试 186 项全过（新增 HouseTest 15 项：状态取值合法性、
          null / 空串回落到「空置」、isRented 一致性；以及「带空白不算合法」这种
          边角）。
        · 连真实数据库的定向验证 20 项全过（R003Probe）：初始化按已成交记录
          标出 101；登记「已成交」后房屋自动置为已租出且提示里说明了这件事；

          手工改回空置生效；传「已售出」被拒且房屋未被改动；
          客户不存在的带看写入失败后房屋状态没有只改一半；概览空置数与实际一致。
        · 无头界面核对 19 项全过（R003UiCheck）：表格 8 列且状态列在下标 4、
          房东三列被正确后移、6 行取值正确（1 已租出 / 5 空置）、
          下拉三个选项且默认「全部」、切「已租出」剩 1 行且正是 101、
          切「空置」剩 5 行且不含 101、切回「全部」恢复 6 行、
          概览页有「空置房源」卡且不再有「平均面积」、卡片总数仍为 5。
        · 对话框结构核对：程序打印出对话框内的全部标签，顺序为

5.6 五个关键改造点
--------------------------------------------------------------------------------

    1. Session 由静态全局变量改为「每请求上下文」——整个改造最关键的一处。

       现状 private static User currentUser 只适用于「同时只有一个用户」的桌面程序。
       Web 端若沿用，A、B 同时登录会互相顶掉身份：B 登录后，A 的所有操作会以
       B 的身份执行，权限控制当场失效。

       方案：JWT + 拦截器 + ThreadLocal（Tomcat 每个请求一个独立线程，
       故「每线程一份」即可让并发请求互不干扰）。权限体系（Permissions 与
       Session.can 的调用方式）保持不变，只是「取当前用户」的来源变了。

    2. DatabaseUtil 里的 Swing 依赖必须摘掉。它是 dao 层的类，却 import javax.swing
       （连库失败弹 JOptionPane），而后端没有图形环境。经核对，整个非界面层
       仅此一处依赖 Swing。

    3. 连接与事务升级：手写的 DatabaseUtil.getConnection 换成 HikariCP 连接池 +
       Spring 声明式事务（@Transactional），替换现有的手写 setAutoCommit 事务。

    4. Result 翻译成 HTTP 语义：Result 内部保持不动，外层用 @RestControllerAdvice
       统一转成 {code, message, data}；DataAccessException 的 Kind 映射为状态码。
       这样两套界面（Swing 与网页）能共用同一份业务返回。

    5. CSV 导出改为下载接口（Content-Disposition: attachment），不再写本地文件。

与方案 5.6 第 3 条的差异：连接池已接入，但 @Transactional 暂未采用。

    原方案：手写的 DatabaseUtil.getConnection 换成 HikariCP + Spring 声明式事务，
            替换现有的手写 setAutoCommit 事务。
    实施：连接池部分照做；事务仍由 core 的 DAO 自己管（setAutoCommit(false) + commit/rollback）。

    原因：@Transactional 要生效，参与事务的取连接动作必须经过 Spring
          （DataSourceUtils.getConnection 或 JdbcTemplate）——Spring 把「本次事务的连接」
          绑在 TransactionSynchronizationManager 上，直接调 dataSource.getConnection()
          会另取一条，事务管不到它。而本项目的 DAO 是「自己取连接、自己关连接」
          （try-with-resources），core 又刻意不依赖任何框架。若让 DatabaseUtil 去调
          DataSourceUtils，等于把 core 绑到 Spring 上——桌面端也得跟着经 Spring 启动，
          与「一套 core 支撑两个界面」的前提直接冲突。

    由此暴露的缺口另行登记为 G-021，并给出两条可选路径。

两点安全上的如实说明：

    1. 退出登录做不到让 token 立刻失效。JWT 是无状态的，服务端没存会话，该接口只记

       要服务端强制失效，需引入黑名单或改用有状态会话。
    2. 房屋列表把房东联系电话一并返回（与桌面端显示一致）。若将来对外提供服务，
       应改为脱敏或按权限返回。

排错记录（两处都是我自己的验证写法有误，产品行为正确，如实记下）：

    · 「篡改 token 仍返回 200」——我改的是签名 Base64 的最后一个字符。Base64 末字符带

      参数而不是 JVM 参数，所以没生效。把 -D 提到 -jar 之前后，确实以退出码 1 拒绝启动。

BUG-002  E 盘上 git 无法写入 refs/remotes（环境问题，非代码缺陷）
--------------------------------------------------------------------------------

现象：在 E 盘的任何仓库中，git update-ref refs/remotes/origin/main <sha> 返回退出码 0
      但 ref 文件不生成；git fetch 报告 [new branch] main -> origin/main 却同样不落盘；
      git fetch --prune 会删掉整个 .git/refs/remotes/origin/ 目录。
结果：git branch -r 为空，git status 持续显示 main...origin/main [gone]。

已排除的可能：
    · 文件权限问题——用 shell 直接写该路径可以成功，且稳定存在
    · 外部进程删除——写入后等待 3 秒、执行无关 git 写操作，ref 均存活
    · 中文路径导致——E:\git-probe-tmp 纯 ASCII 路径同样复现
    · 该仓库损坏——E 盘全新 git init 的临时仓库同样复现
    · git 安装问题——C 盘下同样操作完全正常
    E 盘为正常 NTFS，非网络盘；系统上无第二个 git 安装。

结论：E 盘环境层面的问题，仅影响 refs/remotes 命名空间；refs/heads/** 与自定义
      命名空间（如 refs/probe/thing）均正常。
影响：有限。git push、git ls-remote 正常；git fetch 可经 FETCH_HEAD 取到远端提交。
      仅远程跟踪分支的便利性受损。
规避：需要完整远程跟踪功能时，把仓库放在 C 盘操作，或改用
      remote.origin.fetch = +refs/heads/*:refs/heads/origin/* 映射到本地命名空间。
状态：用户决定暂不处理。

BUG-004  房屋状态列在选中行时文字不可见                     【已修复 2026-09-17】

BUG-005  MySQL 重启后第一次数据库连接失败                  【已修复 2026-09-18】
--------------------------------------------------------------------------------

位置：数据库连接串——db.properties 的 db.url、db.properties.example 模板、
      dao/DatabaseUtil 的内置默认值（三处）

现象：程序启动时报

          java.sql.SQLNonTransientConnectionException:
              Public Key Retrieval is not allowed

      连接直接失败，界面读取不到任何数据。重新运行一次往往又能恢复，
      因此表现为「偶发」。2026-09-18 运行搬迁后的桌面端时暴露。

原因：MySQL 8 的账号默认使用 caching_sha2_password 认证插件。当连接未加密
      （URL 中 useSSL=false）时，首次认证需要向服务端索取 RSA 公钥才能加密口令，
      而 Connector/J 默认禁止该行为（allowPublicKeyRetrieval 默认为 false），
      于是直接报错。

      该公钥索取只在服务端认证缓存未命中时才需要——命中时走 fast path，
      不需要公钥。而认证缓存是内存态，每次 MySQL 重启（含开机）都会清空，
      因此这个缺陷总是在「重启后的第一次连接」出现。

      之所以长期没被发现：mysql 命令行客户端会自动索取公钥，它的连接会把缓存
      填上，之后 Java 再连就命中 fast path 而侥幸成功。也就是说，
      只要先用过命令行客户端，Java 端就不会犯病。

复现与验证（用 FLUSH PRIVILEGES 主动清空认证缓存，构造与重启等价的场景）：

      步骤 1  用带 allowPublicKeyRetrieval 的连接连上并保持
      步骤 2  执行 FLUSH PRIVILEGES 清空认证缓存
      步骤 3  缓存为空时新建连接，逐个试三种 URL：
                ① 原样（useSSL=false，无 allowPublicKeyRetrieval）  → 失败
                ② 追加 allowPublicKeyRetrieval=true                 → 成功
                ③ 去掉 useSSL=false，改用默认 sslMode（走 TLS）     → 成功

修复：连接串追加 allowPublicKeyRetrieval=true，三处同步更新并附原因注释。

      取舍说明：②「不加密连接 + 索取公钥」意味着公钥取自明文信道，理论上存在
      中间人替换公钥的风险；本机开发（localhost）不构成实际问题，且该做法是
      Connector/J 的常规解。若需更稳妥可选 ③（走 TLS），但它依赖服务端已开启
      SSL，故模板默认采用 ②。

      修复后按同样的冷缓存场景复测：桌面端完整跑通（建表 → 读取房屋 / 客户 /
      统计），0 异常。

教训：这类「重启后第一次才犯、之后自愈」的缺陷，靠日常运行几乎不可能稳定复现，
      也就无从定位。必须找到能把内部状态重置的手段（此处是 FLUSH PRIVILEGES
      清空认证缓存），才能把它变成可复现、可验证的问题——与 BUG-003 的
      「验证必须复刻真实执行顺序」同属一类：先造出条件，再谈验证。

RISK-003  联系人字段加密密钥硬编码                 【已修复 2026-09-17】

位置：util/SecurityUtil.java（改造前内含硬编码常量 ENCRYPTION_KEY）

现状（改造前）：AES/ECB/PKCS5Padding 的密钥直接写在源码中。
风险：密钥随源码公开则加密形同虚设；且 ECB 模式并非推荐用法。

G-001  添加操作会静默覆盖已有记录                          【严重】
--------------------------------------------------------------------------------

位置：dao/HouseDAO.java 的 saveHouse()、dao/CustomerDAO.java 的 saveCustomer()

现象：两条 SQL 均写作 INSERT ... ON DUPLICATE KEY UPDATE。因此在「添加房屋」
      对话框里输入一个已存在的 ID，不会报错，而是直接覆盖那套房子的全部字段，
      且界面上没有任何提示。客户同理。

后果：用户以为在新增，实际在改写历史数据，且不留任何痕迹。

建议：三选一
      1. 添加前先按 ID 查一次，存在则提示「ID 已存在」并中止；
      2. 提供独立的「编辑」入口，添加时改用纯 INSERT（冲突即报错）；
      3. 保留覆盖行为，但弹出二次确认「该 ID 已存在，确定覆盖吗？」。
      推荐做法 2 与 3 结合。

G-004  无查询与筛选                                       【重要】

G-005  表头不能排序                                       【重要】
--------------------------------------------------------------------------------

现象：JTable 未启用排序；table.setAutoCreateRowSorter(true) 一行即可开启。
注意：开启后「选中行 → 删除」必须配合 convertRowIndexToModel 做行号转换，
      否则在排序状态下会删错行。这是开启排序时必须一并处理的坑。

实施（阶段三，2026-09-16）：

    · 两张表均开启 setAutoCreateRowSorter(true)，点击表头排序
    · 行号换算已在阶段二就位（getSelectedHouse / getSelectedCustomer 均走
      convertRowIndexToModel），本次开启排序即自动生效，无需再改删除逻辑
    · 额外发现一个必须处理的细节：面积列原先在模型里存的是「格式化后的字符串」，
      而排序器对非 Comparable 类型的列会退化成字符串比较——于是「100」被排在
      「89」之前。改法是把面积以 Double 存入模型，并覆写 getColumnClass 声明为
      Double，显示交给自定义单元格渲染器（AreaCellRenderer）。
      验证：升序得 12.5 / 89.5 / 100，降序相反；反面样本（存字符串）实测得
      100 / 12.5 / 89.5，确为错误顺序。

G-011  密码哈希无盐值                                     【重要】
--------------------------------------------------------------------------------

现象：SecurityUtil.encryptPassword 为 SHA-256(密码) 后直接 Base64，无盐值。
      相同密码产生相同哈希，易被彩虹表反查。
建议：改为 SHA-256(salt + 密码)，每用户独立随机盐。
      注意：改动后须同步更新 users 表中已有的两条记录，否则无法登录。

实施（阶段四，2026-09-16）：

    · encryptPassword 改为「每用户 16 字节随机盐 + SHA-256」，存储格式
      salt:hash（两段均为 Base64；分隔符用冒号——Base64 字符集不含冒号）
    · verifyPassword 同时接受新旧两种格式：不含分隔符的值按旧的无盐哈希校验，
      因此改造不会让已有账号登不进来
    · 密码校验从 SQL 搬到 Java 侧：加盐后每条记录的哈希都不同，
      「WHERE username = ? AND encrypted_password = ?」这种写法已不可能成立
    · 原建议要求「同步更新 users 表中已有记录」，实际采用了更省事的方案：
      旧格式记录在登录成功那一刻自动升级为加盐格式——此时手上正好有明文，
      用户无需重新设密码，也不必手工执行 SQL。
      升级失败不影响本次登录，下次登录会再试
    · 哈希比较改用 MessageDigest.isEqual 而非 String.equals，避免按字符提前返回

    验证（连真实数据库）：
      · admin 改造前库中哈希为 44 字符无盐值
      · 用源码中的预设口令登录成功，登录后变为 69 字符加盐格式
      · 新哈希仍能校验通过；把口令改动一位后仍被拒绝
      · 单元测试另用真实的历史哈希值验证了旧格式兼容路径

G-012  异常处理过于笼统                                   【一般】
--------------------------------------------------------------------------------

现象：DAO 与 Service 层大量使用 e.printStackTrace()，用户侧只看到「添加失败」
      这类笼统提示，分不清是连接失败、主键冲突还是权限不足。

实施（阶段四，2026-09-16）：

    · 新增 util/DataAccessException，把驱动异常归类为 CONNECTION /
      DUPLICATE_KEY / CONSTRAINT / UNKNOWN，并提供 userMessage() 给出面向用户的说明
    · 归类顺序：先看 MySQL 错误码（1062 重复键、1451/1452 外键），
      再看 SQLState（08 开头为连接异常），最后看异常类名。
      刻意不 import 驱动类，保持 util 层与具体数据库解耦
    · 两个 DAO 不再吞掉 SQLException，改为抛出归类后的异常
    · 写操作由 Controller 捕获后转成 Result 文案（主键冲突还会给出
      「该房屋ID已存在，请换一个 ID」这类更贴业务的说法）
    · 读操作则让异常抛到界面层由视图提示，不在控制器里吞成空列表——

    · 界面提示标题也做了区分：读失败显示「读取失败」，保存失败显示「无法保存」
      用户看标题就能判断是自己填错了，还是系统读不到数据
    · 顺带移除 DatabaseUtil.getConnection 里的模态错误框：连接失败的原因现在由
      异常携带，不该在数据层弹窗。这也让无头环境下的自动验证不再被弹框卡住

    验证：单元测试用合成的 SQLException 覆盖了四种归类；实际运行中
    「日志表不存在」被正确归类并在控制台留下记录，且未影响登录成功。

G-018  删除房屋后残留无引用的房东记录             【已修复 2026-09-17】
--------------------------------------------------------------------------------

位置：dao/HouseDAO.java 的 deleteHouse()

现象：删除房屋只删 houses 表记录，landlords 表不做处理。若某个房东只关联了这一套
      房屋，删除后该房东成为孤儿数据——界面上看不到它（系统没有房东管理页），
      但它会一直留在库里。

现状：查看用户现有数据库，已存在此类记录（房东ID 010、1245 等），
      并非本次实施产生，而是自然积累出来的。
      阶段三完成后，概览页的「房东总数」使其变得可见：当前房源 3 套、
      房东 7 位，即 4 位房东未被任何房屋引用。

建议：二选一
      1. 删除房屋后检查该房东是否仍被其它房屋引用，若无则一并删除（与删除同事务）；
      2. 保留现状，待 G-007 提供房东管理页后由管理员自行清理。

说明：与 G-007 相关但可独立处理，故单独编号。

实施（2026-09-17）：采用建议 1。

    改动位置 dao/HouseDAO.java：

      · deleteHouse() 改为事务内三步——先记下该房屋的房东 ID → 删除房屋 →
        该房东若已无任何房屋引用，则一并删除。放在同一事务是必要的：若删房东
        失败而删房屋已提交，留下恰恰是本次要消除的孤儿记录。
      · write() 的编辑分支：先记下原房东，若本次把房屋改挂到别的房东名下且
        原房东因此失去最后一个引用，在同一事务里一并清理。
      · 判断条件写进 SQL 的 NOT EXISTS 子句，而不是「先查数量再由 Java 决定
        删不删」——后者在两步之间留出竞态窗口，前者由数据库在一条语句内
        原子完成。
      · 新增 countHousesByLandlord()，供界面预告「删这套房会顺手删掉房东」。

    界面 view/HouseView.java：删除确认框增加一条提示，且仅在该房东名下没有
      其它房屋时出现——「注意：房东「X」名下没有其它房屋，删除后其房东记录
      将一并清除。」与既有的带看记录级联提示并列，同样遵循「不能悄悄删」。

    比原建议多做的两点：

      1. 原建议只覆盖「删除房屋」，但「编辑时改房东」同样会造成孤儿（房屋
         改挂到别人名下，原房东可能就此无人引用）。一并处理。
      2. 库中已有的 2 条历史孤儿（房东ID 010、31）做了一次性清理。
         清理前整表备份至 .workbuddy/backup/2026-09-17-孤儿房东清理前备份.sql
         （.workbuddy/ 已 gitignore，不入库）。
         清理后房东 7 → 5 位、孤儿 0 条，6 套房屋的房东关联全部完好。

    验证：javac 编译 45 源文件 + 8 测试文件零报错；单元测试 159 项无回归；
      连真实数据库的定向验证 21 项全部通过（覆盖「删独有房东→一并清理」
      「删共有房东→保留，删最后一套才清理」「改房东→清理原房东」
      「改房东但原房东仍被引用→保留」「删不存在的房屋→返回失败不抛异常」，
      以及带看记录级联删除未被事务改造破坏的回归验证）；
      删除确认框按房东独占与共用两种情况分别逐字核对。

G-020  已租出的房源仍可登记带看                             【已修复 2026-09-17】
--------------------------------------------------------------------------------

位置：view/ViewingView.showViewingDialog()、controller/ViewingController

现象：「登记带看」对话框的房屋下拉列出了全部房源，包括已经租出去的那几套。
      现实中不会给一套已租出的房子继续安排带看，这让系统显得不严谨。

    1. 编辑一条旧记录时，要允许它继续挂在已租出的房源上。否则该房源成交之后，
       那条带看记录连改个备注都保存不了（会被规则拦下）。判据是「房屋有没有被
       换过」，因此 DAO 新增 ViewingDAO.findById，用于取原记录比对。
    2. 界面过滤与逻辑拦截必须是同一个定义。界面层的下拉只是体验，逻辑层必须自己
       站得住——将来若从别处（例如批量导入）直接调控制器，也要被拦住。

实现：
    · 新增 util/ViewingRules（纯函数）：isSelectable / selectable / blockReason。
      界面用它过滤下拉，控制器用它做兜底拦截，两边共用一份定义，不会各自漂移。
    · ViewingController.addViewing / updateViewing 增加前置校验；拒绝时给出可执行
      的下一步：「如需重新带看，请先到「房屋管理」把它改回「空置」」。
    · 房屋下拉移除已租出房源并加 tooltip 说明；编辑旧记录时若原房源已租出，
      该项保留并在文字后标注「（已租出）」，免得用户以为过滤失灵。
    · 下拉里一套空置房源都没有时直接提示，而不是弹出一个空列表。
    · HouseDAO 新增 findStatus（只取状态，不读整行、不解密联系方式）。

验证：连库定向探针 24 项全过（空置可登记 / 已租出被拒 / 拒绝原因含下一步 /
      库里没多出记录 / 编辑同一房屋放行 / 换到另一套已租出房源被拒且原记录未变 /
      清理无残留）；单元测试新增 ViewingRulesTest 20 项；

      先出方案再实施的情形区分开。

G-021  跨 DAO 的业务事务边界缺失                             【已登记 2026-09-18】
--------------------------------------------------------------------------------

来源：R-004 阶段 1 实施时发现。方案 5.6 第 3 条原计划「连接池 + Spring 声明式事务」，
      连接池已接入，但 @Transactional 未能采用——原因见 5.12，这里登记由此暴露的缺口。

现状：事务边界只在「一次复合写」内部成立，例如新增房屋 = 写房东 + 写房屋
      （HouseDAO 自己 setAutoCommit(false) 包起来，G-010）。跨多个 DAO 调用的
      业务事务目前没有：譬如「新增客户并同时登记一条带看」这类操作，若第二步失败，
      第一步不会回滚。

影响：现阶段没有真正需要跨 DAO 事务的用例（每个业务操作都只写一组相关表），
      故尚未造成实际问题；但后续阶段（房屋增删改、批量操作、带看模块）
      很可能出现这类操作，届时会变成真实风险。

建议（两条路径，择一）：

    路径 ①  core 的 DAO 改为「连接由外部传入」——已有现成先例：
            HouseDAO.markRented(Connection, ...) 就是这么写的。由调用方控制边界：
            web 层用 Spring 的 TransactionTemplate，桌面端用一个极小的手写模板。
            优点：core 保持框架无关，事务边界显式可见、可测试。
            代价：要改若干 DAO 方法签名，调用点不少。

    路径 ②  core 的 dao 层改用 JdbcTemplate，core 依赖 spring-jdbc。
            换来 @Transactional 注解，写法最简洁。
            代价：core 不再框架无关，桌面端也得经 Spring 启动——
            与「一套 core 支撑两个界面」的初衷冲突。

    倾向：路径 ①。本项目最值得讲的一点正是「同一套业务逻辑支撑两个界面」，
          为省一个注解而放弃它不划算。
